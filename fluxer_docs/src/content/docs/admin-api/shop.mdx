The shop sells owned cosmetic items, bundles of them, premium packages and Visionary in Turkish lira, as [Shop](/http-api/shop/) describes. Every amount on this page is in kuruş, so ₺1 is `100`. These routes set the sales switches, the member discount, the prices and the campaigns, manage the [bundles](#bundles), look up an order, and manage the Visionary numbers. Every route on this page requires `shop:manage` and records an [Admin audit entry](/admin-api/#admin-audit-entry-object), reads included. The routes answer in every premium mode, so an admin can prepare the shop before opening it.

A value the shop cannot accept returns 400 `INVALID_FORM_BODY`, with one element in `errors` that names the field and carries an English message. [Make user a Visionary](/admin-api/users/#make-user-a-visionary) and [Take Visionary from user](/admin-api/users/#take-visionary-from-user) are on the Admin users page.

:::caution[Refunds are made by hand]
Fluxer sends no refund through the payment provider. Refund the payment in the provider's panel, then take back what the order delivered: an item, or each item of a bundle order, with [Take cosmetic item back from user](/admin-api/cosmetics/#take-cosmetic-item-back-from-user), premium time with [End user premium now](/admin-api/users/#end-user-premium-now), or Visionary with Take Visionary from user.
:::

## Minimum price

Every write that changes a price, a campaign or the member discount is checked against the worst case, which is the campaign together with the member discount on an item. A write that would leave any product below ₺1 (`100`) returns 400 `INVALID_FORM_BODY`, and nothing is written. [Create shop order](/http-api/shop/#create-shop-order) checks the final price again.

### Payment provider request budget

The budget is a temporary limit sized for the shop's traffic today. Every API and worker process shares about 2 requests per second to the payment provider, split into three buckets so that none can starve another. Opening orders has about 0.3 per second, callback checks about 0.5 per second, and scheduled checks about 1.2 per second. The shop therefore opens about 0.3 orders per second, roughly 18 a minute, and refuses the rest with 503 `SHOP_BUSY`. The API logs such a refusal at debug level, as expected load shedding, and counts it in `busy_refusals_last_hour`.

The three buckets hold at most 6, 10 and 12 requests, 28 together, which stays under the burst of 30 observed from Payriff. The reconcile job runs once a minute or more often, and each run spends only what the reconcile bucket holds, 12 requests when it is full. While `reconcile_lag_seconds` is above 900, every reconcile run also logs a warning.

Grow the budget when any of these appears:

- `busy_refusals_last_hour` above 0.
- `reconcile_lag_seconds` above 900, which is 15 minutes.
- `provider_backing_off` true, after the first 429 from the provider.
- Daily orders reaching half of the limit the provider approved.

The first step is a higher provider quota, with the three buckets grown together in the same 1 : 1.7 : 4 ratio. The next is a server-side order queue in place of `SHOP_BUSY`. The last is a second payment provider, for which every order already records its provider.

## Shop audit changes

The price and campaign operations record what they changed in the `changes` metadata key. It lists each product whose price or campaign changed as `<sku>:<old>→<new>`, joined with commas, and leaves out a product that stayed the same. The key is absent when nothing changed.

- A price reads as kuruş, such as `premium:1:50000→45000`, and `none` stands for no price.
- A campaign reads as its percentage, such as `20%`, or with its end as `20%@2026-10-01T00:00:00.000Z`, and `none` stands for no campaign.

## Bundles

A bundle sells 2-10 owned-availability items as one product, `bundle:<id>`. [Create shop bundle](#create-shop-bundle) makes it, and it enters the shop once [Set shop prices](#set-shop-prices) gives it a price. Campaigns and the member discount apply as they do to an item. An item sold only in bundles is an owned-availability item with no price of its own.

- A null price takes a bundle out of the shop and keeps it. [Delete shop bundle](#delete-shop-bundle) removes the bundle and its price.
- A bundle leaves the catalog while any of its items is off sale, and cannot be bought until the item is back or the bundle changes.
- A Visionary reward cannot be in a bundle, and an item in a bundle cannot become a Visionary reward.
- An account that owns any item of a bundle cannot buy the bundle, so an item bought alone keeps its buyer from every bundle that holds it.
- An order freezes the bundle's items in `item_ids` when it opens. Open and paid orders deliver those items even after the bundle changes or is deleted.

Delivery gives each item as its own delivery, keyed by the order and the item, then wears the first item of each type it gave in one user update. An item deleted before delivery is skipped, the rest are delivered, the order becomes `granted`, and the API logs a warning with the order and item IDs. Refund by hand.

:::caution[A bundle item the account already owned]
Two orders paid together, such as a bundle and one of its items opened in two tabs, can hold the same item. Only the first delivery gives it, the bundle order still becomes `granted`, and the API logs a warning with the order and item IDs. Refund the whole bundle order, then take back every item it delivered with [Take cosmetic item back from user](/admin-api/cosmetics/#take-cosmetic-item-back-from-user), leaving the item the other order gave.
:::

### Deploying and rolling back bundles

:::danger[Apply the schema first]
The bundle release adds the `shop_bundles` table and the `item_ids` column of `shop_orders`. Apply that schema before the API and worker images. The new code reads `item_ids` with every order, so without the column every order read and write fails, single items included. Without `shop_bundles` the shop catalog, Get shop and the Visionary reward update fail too; `pnpm dev:cassandra:verify` must show both the table and the column.
:::

To roll the bundle release back:

1. Give every `bundle:` product a null price with [Set shop prices](#set-shop-prices), so no bundle order opens.
2. Wait 24 hours after the last bundle order opened, the time of its fourth scheduled check.
3. Check that `reconcile_lag_seconds` in [Get shop](#get-shop) is 0.
4. Roll the code back. The schema only adds, so it stays.
5. For a bundle order still `paid`, give each of its `item_ids` with [Give user a cosmetic item](/admin-api/cosmetics/#give-user-a-cosmetic-item). No route closes an order: it stays `paid` and holds the reconcile cursor until its check row expires after 7 days.

## Update shop settings

<RouteHeader method="PATCH" path="/v1/admin/shop/settings" auditReason />

Opens or closes sales, and sets the member discount and the Visionary settings. Returns the [shop admin settings](#shop-admin-settings-object) object.

### JSON body

| Field | Type | Description |
| --- | --- | --- |
| premium_sales_open? | boolean | The switch for premium packages and Visionary |
| item_sales_open? | boolean | The switch for owned items and bundles |
| premium_discount_percent? | integer | The member discount on items and bundles (0-95) |
| visionary_on_sale? | boolean | Whether Visionary is shown and sold |
| visionary_reward_item_ids? | array[snowflake] | The items delivered and worn with every Visionary number |

An omitted field stays as it is. `payment_provider_configured` and `early_plus_opened_once` are read-only.

- `visionary_reward_item_ids` replaces the list and holds at most 10 IDs. Each must be an owned-availability item without a shop price and in no bundle, and a repeated ID counts once.
- `early_plus_badge_id` is a badge from the catalog whose text has no `{n}`, or null. It needs `badges:manage` as well. Once Early Plus has opened, the badge is fixed for good. Choose a badge made only for Early Plus, because a take-back removes that badge even when an admin gave it by hand.
- `early_plus_open` set to true needs `badges:manage` as well, and a badge. Closing needs only `shop:manage`.

### Response

| Status | Body | Condition |
| --- | --- | --- |
| 200 | [shop admin settings](#shop-admin-settings-object) object | The settings were saved |
| 400 | [error response](/admin-api/#error-response) | A value is refused, or a product would fall below the [minimum price](#minimum-price) |
| 403 | [error response](/admin-api/#error-response) | `MISSING_ACL`, because the request chooses the Early Plus badge or opens Early Plus without `badges:manage` |

### Side effects

The settings are saved with a compare-and-set, and every API process picks them up through the instance configuration refresh. The shop catalog can show the old values for up to 60 seconds. A new reward item reaches only numbers delivered after the change.

While Early Plus is open, every delivered premium or Visionary order gives its buyer the Early Plus badge. Gift codes, admin grants, referral rewards and trials do not, and neither does an order support refunds by hand: a premium order paid by a Visionary, or a Visionary order paid by an account that already is one. Every request that sets `early_plus_open` to true queues a `backfillEarlyPlusBadges` job, at most one a minute, shown on the jobs page. The job gives the badge to the buyer of every premium order delivered so far, and of every Visionary order whose buyer still is a Visionary. It skips deleted accounts and accounts with the `EARLY_PLUS_REFUNDED` [premium flag](/admin-api/users/#premium-flags). Its result holds `granted`, `scanned` and `duration_ms`, and a cancel on the jobs page stops it. Closing stops new badges. Badges already given stay.

Ending paid premium and taking Visionary back both take the badge away and set `EARLY_PLUS_REFUNDED`, and the next delivered premium or Visionary order clears the flag. A refund made before Early Plus existed has no flag, so its badge must be taken away by hand.

The operation records one [Admin audit entry](/admin-api/#admin-audit-entry-object) with action `update_shop_settings`, target type `shop`, and target ID `0`. For every field the request changed, the metadata holds `<field>_old` and `<field>_new`.

### Rate limit

30 requests per minute for each authenticated user, on the `admin:shop:manage` bucket.

## Set shop prices

<RouteHeader method="PUT" path="/v1/admin/shop/prices" auditReason />

Sets the list price of up to 200 products, and returns the [shop admin](#shop-admin-object) object. The `visionary` product is priced here too.

### JSON body

| Field | Type | Description |
| --- | --- | --- |
| prices | array[[shop price entry](#shop-price-entry-object) object] | The prices to set (1-200 entries) |

- A cosmetic SKU must name an owned-availability item, and a Visionary reward item cannot take a price.
- A bundle SKU must name an existing [bundle](#bundles). A null price is accepted for any bundle SKU, which clears a price left behind by a deleted bundle.
- A new price keeps the product's campaign. A null price removes the product and its campaign.
- A SKU repeated in the list takes its last value.

### Response

| Status | Body | Condition |
| --- | --- | --- |
| 200 | [shop admin](#shop-admin-object) object | The prices were set |
| 400 | [error response](/admin-api/#error-response) | An entry is refused, or a product would fall below the [minimum price](#minimum-price) |

### Side effects

A quote shows a new price within 5 seconds and the catalog within 60 seconds. An order opened after the write is charged the new price.

The operation records one [Admin audit entry](/admin-api/#admin-audit-entry-object) with action `set_shop_prices`, target type `shop`, target ID `0`, and metadata keys `count`, `skus`, the SKUs joined with commas, and `changes`, as [Shop audit changes](#shop-audit-changes) describes.

### Rate limit

30 requests per minute for each authenticated user, on the `admin:shop:manage` bucket.

## Apply shop campaign

<RouteHeader method="POST" path="/v1/admin/shop/campaigns" auditReason />

Puts one campaign discount on up to 200 priced products, until the given time or with no end, and returns the [shop admin](#shop-admin-object) object. Visionary takes campaigns too. It never takes the member discount, which items still take on top of the campaign.

### JSON body

| Field | Type | Description |
| --- | --- | --- |
| skus | array[string] | The [products](/http-api/shop/#shop-products), each with a price (1-200 entries) |
| percent | integer | The campaign discount (1-95) |
| ends_at | ?ISO8601 timestamp | When the campaign ends, in the future, or null for no end |

A campaign replaces the product's previous one, and a repeated SKU counts once. The campaign ends by the server clock. Its row keeps the percentage until it is removed or replaced, and `now` shows the price without it.

### Response

| Status | Body | Condition |
| --- | --- | --- |
| 200 | [shop admin](#shop-admin-object) object | The campaign was applied |
| 400 | [error response](/admin-api/#error-response) | A SKU has no price, the end is in the past, or a product would fall below the [minimum price](#minimum-price) |

### Side effects

The operation records one [Admin audit entry](/admin-api/#admin-audit-entry-object) with action `apply_shop_campaign`, target type `shop`, target ID `0`, and metadata keys `count`, `percent`, `ends_at` and `changes`, as [Shop audit changes](#shop-audit-changes) describes.

### Rate limit

30 requests per minute for each authenticated user, on the `admin:shop:manage` bucket.
