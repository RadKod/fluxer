The shop sells four kinds of product, priced and charged in Turkish lira (TRY): owned [cosmetic items](/http-api/cosmetics/), [bundles](#shop-bundle-object) of such items, premium packages of 1, 3 or 12 months, and [Visionary](#visionary). Every amount is in kuruş, so ₺1 is `100`, and no amount is ever converted to another currency. The server computes every amount, and a client sends only the product. The [Admin API](/admin-api/shop/) sets the prices, campaigns and sales switches.

Every route on this page is user-only, except [Get code preview](#get-code-preview) and the two payment callback routes, which take no credential. The catalog, quote and order routes answer only on a self-hosted instance in the `mirror` [premium mode](/admin-api/instance/#premium-modes). Any other instance returns 403 `FEATURE_NOT_AVAILABLE_SELF_HOSTED`.

:::note[Sales start closed]
Both sales switches start off. The shop takes money only while the deployment has a payment provider configured. The one integration today is Payriff, which is off unless the deployment enables it. Without a provider the shop reports both sales closed whatever the switches say: the catalog still lists the products, the quote and order routes return 403 `SHOP_SALES_CLOSED`, and items and premium time are given through [gift codes](/http-api/gifts/) and admin grants.
:::

## Shop products

A product is named by its SKU.

| Value | Description |
| --- | --- |
| `cosmetic:<item_id>` | An owned-availability [cosmetic item](/http-api/cosmetics/#cosmetic-item-object), by its ID |
| `bundle:<bundle_id>` | A [bundle](#shop-bundle-object) of 2-10 owned-availability items, by its ID |
| `premium:1`, `premium:3`, `premium:12` | Premium time of 1, 3 or 12 months |
| `visionary` | Lifetime premium with a [Visionary](#visionary) number |

An item or bundle ID is a positive integer within the signed 64-bit range. A value of any other shape fails validation with 400 `INVALID_FORM_BODY`.

## Prices

The server computes a price in one place, in whole numbers:

1. The campaign discount comes off the list price while the campaign has not ended by the server clock.
2. The premium member discount comes off that, for cosmetic items and bundles only, and only for an account with paid premium. An account in its free trial gets no member discount. Lifetime premium counts as paid.

Each step rounds half up, and the result is the amount charged. A list price of ₺500 (`50000`) with a 20% campaign and a 30% member discount comes to ₺400 (`40000`), then ₺280 (`28000`). A product whose final price would fall below ₺1 (`100`) is not sold.

Premium packages and Visionary take campaigns, and never take the member discount.

Each API process keeps the catalog for up to 60 seconds, and the quote reads a price list kept for up to 5 seconds, so both are for display. [Create shop order](#create-shop-order) reads the stored price and settings directly, and the amount it records is the amount charged.

## Shop refusals

The quote and order routes refuse a product with these codes:

- 403 `SHOP_SALES_CLOSED` when sales of the product's kind are closed or no payment provider is configured. Premium packages and Visionary follow the premium sales switch, and cosmetic items and bundles follow the item sales switch.
- 404 `SHOP_ITEM_UNAVAILABLE` when the product has no price or no longer exists, when an item, or any item of a bundle, is not an owned-availability item on sale, when the final price would fall below ₺1, when an account with lifetime premium asks for a package or Visionary, or when Visionary is switched off. An order also receives it when no Visionary number is free.
- 409 `COSMETIC_ALREADY_OWNED` when the account already owns the item, or any item of a bundle. A bundle is never sold in part.
- 409 `SHOP_TOO_MANY_OPEN_ORDERS`, on an order only, when the account already has three open orders. An open order is unpaid, less than 15 minutes old, and not declined, cancelled or expired at the payment provider.
- 503 `SHOP_BUSY`, on an order only, when the shared payment provider request budget is spent, when the provider is backing off after a 429 or did not open the order, or while another order of the same account is being opened. Retrying after a few seconds is safe.

## Payment and delivery

1. [Create shop order](#create-shop-order) returns an order with `payment_url`, the payment provider's page, which a client opens in the browser.
2. The provider calls [Receive Payriff callback](#receive-payriff-callback) when the payment changes, and the browser comes back through [Return from Payriff](#return-from-payriff). Neither is trusted. A matching callback token only queues a check, in which the server reads the order from the provider.
3. The check accepts a payment only when the provider reports it `APPROVED` or `PAID` for a purchase, in the order's currency, for exactly the amount of the order. The order becomes `paid`, is delivered, and becomes `granted`.
4. A client follows the order with [Get shop order](#get-shop-order), which reads only the server's record and never reaches the provider.

Apart from callbacks, the server checks every unpaid order with the provider 2 minutes, 15 minutes, 3 hours and 24 hours after it opened. An order still unpaid at the fourth check expires, and so does an order the provider reports expired. An order that has no provider order ID 10 minutes after it opened fails with `provider_error`.

Scheduled checks leave an expired order alone, so only a callback or a return finds a payment made after the order expired. The check that finds it makes the order `paid` and schedules one more check 2 minutes later, so the delivery still completes when the callback check gives up. A paid order whose delivery has to wait keeps its scheduled check until the delivery finishes.

Delivery depends on the product:

- A cosmetic item is added to the account and worn in the slot of its type. Deliveries of one item to one account run one at a time, and a delivery that waits more than about 5 seconds is tried again later. That sends [User Update](/gateway/events/#user-update), and for an avatar decoration, ultra decoration or nameplate also [Guild Member Update](/gateway/events/#guild-member-update), as [Wear or take off cosmetics](/http-api/cosmetics/#wear-or-take-off-cosmetics) does.
- A bundle delivers each item in the order's `item_ids` as its own delivery, the way a cosmetic item is delivered, and wears only the first item of each type in that list. The other items are added without being worn. A delivery that stops part way is tried again later and gives only the items still missing.
- A premium package adds its months to the account's premium and sends User Update.
- Visionary is delivered as [Visionary](#visionary) describes.

:::caution[An order delivers once]
Callbacks, returns and scheduled checks can arrive together, and an order is still delivered once. Delivery runs only on a `paid` order, and a lasting delivery record for each order stops a second delivery. An item, premium time or Visionary number an admin takes back afterwards never comes back from the same order, and an admin taking an item back while its delivery runs wins.
:::

A payment for an item the account already owns when the delivery runs grants no second copy, and neither does a second paid order for the same item delivered at the same time. The order becomes `granted`, and an admin refunds the payment by hand.

A paid cosmetic order whose item was deleted before delivery fails with `item_deleted`, and an admin refunds it by hand too.

A bundle order skips an item deleted before delivery and an item the account already owns, delivers the rest, and becomes `granted`. An admin refunds it by hand, as [Bundles](/admin-api/shop/#bundles) in the Admin API describes.

## Order records

An order is a financial record. Deleting the account keeps its orders, which hold the account ID, the product, the items of a bundle order, the amounts in kuruş, the currency, the payment provider and its order ID, and the times, and no email address, name or IP address. The [data harvest](/http-api/users/data-harvest/) lists every order of the account, newest first, without the payment page, whether or not a payment provider is configured.

## Visionary

Visionary is lifetime premium with a number. The admin sets the price, the number of numbers, and whether Visionary is on sale. The catalog carries a [shop Visionary](#shop-visionary-object) object once the price is set. It stays in the catalog when every number is taken, with `remaining` at 0.

The `visionary` product takes campaigns, and never takes the member discount. It follows the premium sales switch, so closed premium sales return 403 `SHOP_SALES_CLOSED`. A switched-off Visionary, a missing price, or an account that already has lifetime premium, whether as a Visionary or not, returns 404 `SHOP_ITEM_UNAVAILABLE`.

Numbers are handed out as follows:

- [Create shop order](#create-shop-order) holds the lowest free number for 15 minutes before it asks the payment provider. When no number is free, it returns 404 `SHOP_ITEM_UNAVAILABLE` and the provider is never called.
- An order that fails or expires unpaid frees its number.
- A payment that arrives after the hold ended still gets a number: the held one if it is still free, otherwise the next free one, otherwise one above the total. The Admin API counts a number above the total in `over_cap_grants`.
- An account that is already a Visionary when its order is delivered gets no second number. The order still becomes `granted`, the number it held is freed because it was never any account's number, and an admin refunds the payment by hand. Two orders of one account delivered together give one number.
- A number is never given twice. A number an admin takes back, or one whose account is deleted, stays retired and is never sold again. An order whose number an admin took back never gives it again, even when its delivery is retried.

Delivery gives the account lifetime premium, with the number as its premium lifetime sequence, and the reward items the admin chose, each added and worn. It runs under the account's premium lock, as [Make user a Visionary](/admin-api/users/#make-user-a-visionary) does. While another premium change holds that lock, the delivery is tried again later. The account's sessions receive [User Update](/gateway/events/#user-update). The shop joins no Visionary guild.

In the `mirror` premium mode, only an account with lifetime premium can take the discriminator `0000`. An account that already wears `0000` keeps it until it changes its username, and must then pick another discriminator. Otherwise the change fails with 400 `INVALID_FORM_BODY` and the validation code `VISIONARY_REQUIRED_FOR_DISCRIMINATOR`.

## Create shop order

<RouteHeader method="POST" path="/v1/shop/orders" />

Opens a payment provider order for one product at the price the server computes now, and returns the [shop order](#shop-order-object) object with its payment page. The order is delivered once the provider confirms the payment, as [Payment and delivery](#payment-and-delivery) describes.

An open order of the account for the same product at the same amount, and for a bundle with the same items in the same order, is returned instead of a new one, so repeating the request opens no second payment.

### Limitations

- The account must be claimed, and an unclaimed account returns 400 `UNCLAIMED_ACCOUNT_CANNOT_MAKE_PURCHASES`.
- The account must have a verified email address, and an unverified address returns 403 `PURCHASE_EMAIL_VERIFICATION_REQUIRED`.
- The account must not have the purchase-disabled premium flag, which returns 403 `PREMIUM_PURCHASE_BLOCKED`.
- Every [shop refusal](#shop-refusals) applies.

### JSON body

| Field | Type | Description |
| --- | --- | --- |
| sku | string | The [product](#shop-products) to buy |

### Response

| Status | Body | Condition |
| --- | --- | --- |
| 200 | [shop order](#shop-order-object) object | The order was opened, or an open order for the same product and amount was returned |
| 400 | [error response](/http-api/#error-response) | The SKU fails validation, or the account is unclaimed |
| 403 | [error response](/http-api/#error-response) | Sales are closed, purchases are not allowed for the account, or the instance has no shop |
| 404 | [error response](/http-api/#error-response) | The product cannot be bought now, returned as `SHOP_ITEM_UNAVAILABLE` |
| 409 | [error response](/http-api/#error-response) | The account owns the item or an item of the bundle, or already has three open orders |
| 503 | [error response](/http-api/#error-response) | The server cannot open a payment provider order now, returned as `SHOP_BUSY` |

### Side effects

The order is written as `pending` with the amounts of the one price computation, and its first scheduled check is set. A Visionary order holds a number before the payment provider is asked. A bundle order records the bundle's items in `item_ids`, and a later change to the bundle, or its deletion, leaves them as they are. The catalog can be up to 60 seconds old, so a client compares `item_ids` with the items it showed before it opens the payment page. The order description sent to the provider names the product, the price in lira and the order ID, so an admin can find the order with [Get shop order](/admin-api/shop/#get-shop-order) in the Admin API. When the provider does not open the order, the order fails with `provider_error`, its Visionary number is freed, and the request returns 503 `SHOP_BUSY`.

### Rate limit

3 requests per minute for each authenticated user, on the `shop:order:create` bucket. 20 requests per day for each authenticated user, on the `shop:order:create:day` bucket.

## Return from Payriff

<RouteHeader method="GET" path="/v1/payriff/callback/{order_id}/{token}" unauthenticated />

The browser lands here from the payment provider's page. The route redirects it to the premium callback page of the web app with a status and no order detail. It never answers with an error.

### Path parameters

| Field | Type | Description |
| --- | --- | --- |
| order_id | string | The ID of the order |
| token<sup>1</sup> | string | The callback token of the order |

<sup>1</sup> 32 random bytes in base64url, created with the order. It exists only in the callback address handed to the provider. The server keeps its SHA-256 hash and compares in constant time, and the request and error logs write the path with the token masked

### Response

| Status | Body | Condition |
| --- | --- | --- |
| 302 | empty | Always, with `Location` set to `/premium-callback?status=` on the web app and one of the statuses below |

- `success` when the order is granted, or paid and waiting for delivery.
- `cancel` when the order failed.
- `pending` in every other case: an unpaid or expired order, a token that does not match, an unknown or malformed order ID, or a server error.

### Side effects

A matching token queues a check of the order with the provider, as [Payment and delivery](#payment-and-delivery) describes. Repeats within 30 seconds queue one check, and each order takes at most 10 callback checks an hour, so replaying a return link cannot spend the provider request budget. The scheduled checks run whatever the callbacks do. Anything else queues nothing.

### Rate limit

600 requests per minute for each client IP address, or for the authenticated user when a credential happens to be supplied, on the `payriff:callback` bucket.

## Receive Payriff callback

<RouteHeader method="POST" path="/v1/payriff/callback/{order_id}/{token}" unauthenticated />

Payriff calls this when a payment changes. Payriff signs nothing, so the body is never read. Only the order ID and the token in the path count, with the same [path parameters](#return-from-payriff) and side effects as [Return from Payriff](#return-from-payriff). Returns a [webhook received](/http-api/billing/#webhook-received-object) object.

### Response

| Status | Body | Condition |
| --- | --- | --- |
| 200 | [webhook received](/http-api/billing/#webhook-received-object) object | Always, unless the caller accepts `text/html` |
| 303 | empty | The caller accepts `text/html`, and is sent where [Return from Payriff](#return-from-payriff) would send it |

### Rate limit

600 requests per minute for each client IP address, or for the authenticated user when a credential happens to be supplied, on the `payriff:callback` bucket.
